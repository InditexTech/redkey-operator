# Object Overrides

Redkey generates a set of Kubernetes objects for every cluster (a `StatefulSet`
for the Redis nodes, a headless `Service`, a `ConfigMap` and, optionally, a
`PodDisruptionBudget`). The **object overrides** feature lets you customize the
generated `StatefulSet` and `Service` without forking the operator, by supplying
a partial manifest that is merged on top of the generated one.

Overrides are useful for things the operator does not expose as first-class
fields, such as pod scheduling constraints (`nodeSelector`, `tolerations`,
`affinity`, `topologySpreadConstraints`), extra annotations/labels, sidecar
containers, additional volumes, or extra service ports for metrics exporters.

> **Scope.** Only the Redis `StatefulSet` and the headless `Service` can be
> overridden. The generated `ConfigMap`, `PodDisruptionBudget` and the Robin
> `Deployment` are **not** overridable.

## Specifying overrides

Overrides live under `spec.override` of the `RedkeyCluster` (and are propagated
to the `RedkeyClusterConfig` consumed by Robin):

```yaml
apiVersion: redkey.inditex.dev/v1beta1
kind: RedkeyCluster
metadata:
  name: my-cluster
spec:
  primaries: 3
  replicasPerPrimary: 1
  image: redis:8
  override:
    statefulSet:
      metadata:
        annotations:
          backup.io/enabled: "true"
        labels:
          tier: cache
      spec:
        template:
          spec:
            nodeSelector:
              disktype: ssd
            tolerations:
              - key: dedicated
                operator: Equal
                value: redis
                effect: NoSchedule
            containers:
              - name: redis
                resources:
                  limits:
                    memory: 2Gi
              - name: redis-exporter
                image: oliver006/redis_exporter:latest
                ports:
                  - name: metrics
                    containerPort: 9121
    service:
      metadata:
        annotations:
          prometheus.io/scrape: "true"
      spec:
        ports:
          - name: metrics
            port: 9121
            targetPort: 9121
```

## Merge semantics

Overrides are applied using a Kubernetes **strategic merge patch** against the
object generated by Robin. Strategic merge respects the patch-merge keys of the
underlying types, which means:

- **Lists keyed by name** (containers, volumes, ports, env entries…) are merged
  by their `name`. To customize the generated `redis` container, add an entry
  with `name: redis` containing only the fields you want to change — the rest of
  the generated container is preserved. New entries (for example a sidecar
  container or an extra volume) are appended.
- **Maps** (annotations, labels, `nodeSelector`…) are merged key by key. Keys you
  do not mention keep their generated value.
- **Scalars** you set replace the generated value.

Removing an override (or one of its fields) reverts the corresponding object back
to the generated default on the next reconciliation, because Robin always rebuilds
the object from scratch before applying the (possibly empty) patch.

## Guard rails

To keep the cluster functional, a set of fields is **always restored** to the
operator-managed value after the merge, even if the override tries to change them.

### StatefulSet

| Field | Enforced value |
|-------|----------------|
| `spec.replicas` | Managed by the operator (derived from topology). |
| `spec.serviceName` | The generated headless Service name. |
| `spec.selector` | The generated cluster selector. |
| `spec.template.spec.containers[redis]` | The `redis` container is always present and kept at index 0. You may patch its fields, but you cannot remove it. |
| `spec.template.spec.volumes` | The required `config` and `data` volumes are always present. |
| `spec.volumeClaimTemplates` | Preserved from the generated object unless the override provides its own. |

### Service

| Field | Enforced value |
|-------|----------------|
| `spec.clusterIP` | `None` (the Service stays headless). |
| `spec.selector` | The generated cluster selector. |
| `spec.ports` | The required `client` and `gossip` ports are always present. |

Any other field is yours to override. If the override happens to set one of the
guarded fields, the value is silently ignored in favor of the operator-managed one.

## Examples

### Schedule Redis pods on dedicated nodes

```yaml
spec:
  override:
    statefulSet:
      spec:
        template:
          spec:
            nodeSelector:
              workload: redis
            tolerations:
              - key: dedicated
                operator: Equal
                value: redis
                effect: NoSchedule
```

### Add a metrics exporter sidecar and expose it

```yaml
spec:
  override:
    statefulSet:
      spec:
        template:
          spec:
            containers:
              - name: redis-exporter
                image: oliver006/redis_exporter:latest
                ports:
                  - name: metrics
                    containerPort: 9121
    service:
      metadata:
        annotations:
          prometheus.io/scrape: "true"
          prometheus.io/port: "9121"
      spec:
        ports:
          - name: metrics
            port: 9121
            targetPort: 9121
```

The generated `redis` container, the `client`/`gossip` service ports and the
headless `clusterIP: None` are all preserved automatically.
